# kuchiku

[![License: MIT](https://img.shields.io/badge/License-MIT-yellow.svg)](./LICENSE)

## これは何？

日本語の文章（Markdown）から、**文章の主眼に関係ない節・本文の再掲・前置き・中身のない文**を見つけ、**削除だけ**で短くする Claude Code スキル（`/kuchiku`）です。

AIっぽさを判定するツールではありません。人が書いた水増しも、AIが書いた節も、文章の主眼を基準に判定します。文の書き換えはしません。

## 背景と課題

1. 「AIっぽいかどうか」で削ると、人が書いた水増しは残り、AIが書いた必要な節が消える
2. LLM に「短くして」と頼むと、文を書き換える過程で、新しいAIっぽさや事実の改変が混ざる
3. 何を消してよいかは文章ごとの「主眼」で決まるが、それを先に決める手順がない

## 本スキルのアプローチ

### 3つの方針

1. **判定の軸は「主眼」**: 文章が読者に伝えたいこと（構造シートの「主眼」など）を一文で決め、本人が確認してから判定します。問いは「これを消しても主眼は守れるか」だけです。
2. **削除だけで縮める**: LLM に許すのは「どの単位を消すか」の選択だけです。短縮版は原文の部分列になり、スクリプトがそれを機械的に検証します。直す過程で新しいAIっぽさが混ざりません。
3. **自分の判断で育てる**: 採否と却下理由を記録し、採用率の低い提案パターンは次回から控えます。

### 削る対象（5分類）

| 分類 | 例 |
|---|---|
| 主眼と無関係 | 比較の文章なのに、片方のツールの歴史を長く説明している |
| 再掲 | まとめの箇条書きが本文の注意点をそのまま繰り返している |
| 一般論 | 主題を別のツールに差し替えても成立する「生産性が向上します」 |
| 前置き | 「本記事では〜について解説します」 |
| 中身のない文 | 「いかがでしたか」「今後ますます重要になるでしょう」 |

手順・数値・条件・判断基準・限界の明記は削りません。各案は「消すと再現できなくなるか」「消すと結論が変わるか」の両方が「いいえ」でなければ通りません。

### 流れ

```
 文章.md
   │
   ├─ plan ───── 文・項目・ブロック単位に分け、IDを振る
   │             機械ヒント（定型句・再掲・情報密度・汎用見出し）
   │             主眼の候補（構造シートなど）
   │
   ├─ Claude が plan.json（削除案）を書く（消す単位・分類・理由・削除テスト）
   │
   ├─ apply ──── （主眼が未確認の間）plan.json を検査して結果を見せる
   │             削除だけを適用 → cut.md、report.md（文章は変わらない）
   │             原文の部分列かを検証（書き換えがあれば止まる）
   │
   ├─ 主眼と削除案を本人が1回で確認  ← ここは省略できない
   │
   └─ apply ──── （主眼を確認後）accepted が true の案を文章に反映
                 採否を decisions.jsonl に記録 → learned.md を更新
```

## Before → After 例

架空の文章で実行した結果です。主眼は「git worktree を使うと、作業中のブランチを切り替えずに別ブランチの PR をレビューできる」。

### Before

```markdown
## はじめに

本記事では、git worktree を活用することで、開発効率を大幅に向上させる方法について解説します。
現代のソフトウェア開発において、複数のタスクを並行して進めることは非常に重要です。
さまざまな場面で役立つテクニックなので、ぜひ最後までご覧ください。

## git worktree とは？

git worktree とは、1 つのリポジトリに対して複数の作業ディレクトリを持てる機能です。
Git 2.5 で追加されました。
この機能を活用することで、柔軟な開発フローを実現することができます。
```

### After

```markdown
## git worktree とは？

git worktree とは、1 つのリポジトリに対して複数の作業ディレクトリを持てる機能です。
Git 2.5 で追加されました。
```

### 変更説明

| # | 対象 | 分類 | 理由 |
|--:|---|---|---|
| 1 | 「はじめに」の節ごと | 前置き | 文章の予告と一般論だけで、手順に関わる情報がない |
| 2 | 「この機能を活用することで、…」など3文 | 中身のない文 | どの文章にも書ける締めの文で、主眼に関わる情報がない |

この例では本文が 1,192字 → 946字（−246字、約21%）になります。コマンドの手順、数値（約 40 秒）、エラーメッセージの対処は、1文字も変わりません。

## インストール

### 1. Claude Code プラグイン

インストール手順

```
/plugin marketplace add ttomo-ttomo/kuchiku
/plugin install kuchiku@kuchiku
```

### 更新

ターミナルで次を実行して、Claude Code を再起動します。

```bash
claude plugin marketplace update kuchiku
claude plugin update kuchiku@kuchiku
```

### アンインストール

ターミナルで次を実行して、Claude Code を再起動します。

```bash
claude plugin uninstall kuchiku@kuchiku
claude plugin marketplace remove kuchiku
```

対象のリポジトリにできた `.kuchiku/`（判断ログなど）は消えません。不要なら手で削除してください。

## 使い方

Claude Code で:

```
/kuchiku docs/my-text.md
```

ディレクトリも渡せます。配下の `.md` をまとめて分析し、文章ごとの一覧（`overview.md`）を出します。

1. 主眼の一文、構造シート（項目ごとの A/B/C）、削除案の一覧（番号・対象・分類・削減字数・理由）が**1つにまとめて**出ます
2. 主眼の確認と、採用する番号を一度に答えます（却下の理由を一言添えると、次回の提案に反映されます）
3. 答えた内容で、元の文章が書き換わります（`git diff` で確認できます。主眼を直したときは案を作り直して、もう一度見せます）

### 主眼の決め方

次の順で探し、見つからなければ文章から書き出して確認します。

1. 文章内の `<!-- promise: 主眼の一文 -->`
2. `drafts/<文章名>-structure-sheet.md` などの構造シートにある「主眼: …」（優先度 A/B/C の表も読みます）

### 削らせたくない節

`<!-- kuchiku:keep -->` を置きます（その節と子の節がロックされます）。構造シートで優先度 A の節も削られません。

### 作業ファイル

対象のリポジトリ直下の `.kuchiku/` にできます。`runs/` と `overview.md` を除外する `.gitignore` が `.kuchiku/` の中に自動で作られるので、対象側の `.gitignore` の編集は要りません。判断ログ（`decisions.jsonl`）と `learned.md` はコミットします。置き場所は環境変数 `KUCHIKU_HOME` で変えられます。

## コマンドとオプション

普段は `/kuchiku 文章.md`（ディレクトリも可）と打つだけで、Claude が下のコマンドを呼びます。主眼と削除案は**1回の確認**で聞かれます。

実行ファイルは `skills/kuchiku/bin/kuchiku` です。

| コマンド | 引数 | 内容 |
|---|---|---|
| `plan` | `<文章.md \| ディレクトリ>` | 文章を削除単位に分け、機械ヒントと主眼の候補を書く。文章は変えない。ディレクトリなら配下の `.md` すべてに実行し、`overview.md` に一覧する |
| `apply` | `<文章.md \| ディレクトリ>` | `plan.json`（削除案）を検査し、削除だけを適用した `cut.md` と `report.md` を作って見せる。`plan.json` の `promise_confirmed` が `true` なら、`accepted` が `true` の案を文章に反映し、採否を記録する（`false` の間は文章を変えない）。実行のたびに `plan.json` を検査し直す。ディレクトリなら `plan.json` のある文章すべてに実行する |
| `verify` | `<元の文章.md> <縮めた版.md>` | 縮めた版が、原文から削除しただけでできているかを確かめる。`apply` は内部で毎回実行し、結果を `verified` に出すので、手で縮めた版を確かめるときだけ使う |
| `stats` | `[リポジトリのパス]` | 採否の傾向を表示し、`learned.md` を更新する |

**オプションはありません。** 何を反映するかは、`plan.json` に書きます。Claude が、`apply` の前に次を書き足します（利用者は触りません）。

| `plan.json` の項目 | 値 | 説明 |
|---|---|---|
| `promise_confirmed` | `true` / `false` | 主眼を本人が確認したか。`true` になって初めて、`apply` が文章を書き換える |
| `cuts[].accepted` | `true` / `false` | 各案を採用するか。全案に書く（書き忘れると止まる）。`false` の案は却下として記録される |
| `cuts[].note` | 文字列 | 却下の理由。次回以降の提案の傾向（`learned.md`）に使われる |

`plan.json` は、Claude が決めた削除案・主眼・構造シートの優先度・採否を `apply` コマンドに渡すファイルです（run ディレクトリに置かれます）。

例:

```bash
kuchiku plan docs/                       # 分析
kuchiku apply docs/x.md                  # plan.json を検査して見せる。確認済み（promise_confirmed）なら採用された案を反映
kuchiku apply docs/                      # plan.json のあるすべての文章に実行
```

## 限界

- 文の区切りは日本語の句点（。！？）が前提です。英語の文章は文単位で扱えません
- 表・コードブロック・`:::` ブロック・引用は丸ごと1単位で、中の行だけは消せません
- 番号付きリストの途中を消すと番号が飛びます（表示は Markdown の番号振り直しに任せます）
- 情報密度は弱い指標です。体験談やエッセイの節は、必要でも低く出ます
- 何を消すかの判断は LLM が行います。スクリプトが保証するのは「削除しかしていないこと」と「主眼が確認済みであること」です
