# kuchiku: 削除だけで文章を縮める

対象: $ARGUMENTS（文章1本か、ディレクトリ。指定がなければ聞く）

このスキルは、文章を「主眼を守れる最短版」に近づける。やることは**削除の提案だけ**で、言い換え・要約・書き足しはしない。削除だけなので、直す過程で新しいAIっぽさが混ざらない。

`<skill>` はこの SKILL.md があるフォルダを指す。コマンドは Go 製の1本の実行ファイル `<skill>/bin/kuchiku` で、以下では `kuchiku` と書く。`bin/` には OS・CPU別のビルド済み実行ファイル（linux・mac・windows）が入っていて、`kuchiku` が自動で選ぶ。Go は不要。

## 手順

### 1. 構造シートで分析する

削る前に、文章を構造シートにして、何が主眼で、どこが重いかをつかむ。ルールは [structure-sheet.md](https://github.com/ttomo-ttomo/zenn-article/blob/main/writing-guide/rules/structure-sheet.md)。文章を頭から読み、次の順で作る。

1. 項目を書き出す。長い文章は章（見出し）、短い文章は話題を1行にする。文章の出てくる順に番号を振る
2. 項目全体を眺めて、主眼を一文で書く。「結局これは何の話か」を、この文章ならではの切り口で書く。項目を出し終えてから書く
3. 各項目にA・B・Cを付ける。順番とは別に決める

| 優先度 | 判定の問い |
|---|---|
| A | これがないと主眼が成り立たないか（原則1つ） |
| B | 読者の理解や行動に必要か |
| C | 省いても主眼は伝わるか |

表と主眼を本人に見せる。このシートは手順3以降で次のように使う。
- 主眼は、手順3で決める主眼の候補になる
- Cの項目は、削除案を探す優先場所になる
- Aの項目は削らない。手順4の `plan.json` の `structure` に節ごとの優先度を書くと、Aの節を消す案は apply が弾く

文章に構造シートや `<!-- promise: … -->` がすでにあれば、作り直さずそれを使う。

### 2. plan: 文章を分析する

```bash
<skill>/bin/kuchiku plan <文章.md | ディレクトリ>
```

**ディレクトリを渡したとき**: 配下の `.md` をすべて分析し（`.` で始まるフォルダと node_modules は除く）、文章ごとの本文字数・主眼の候補・目印のある節を `overview.md` にまとめる。この一覧を本人に見せ、どの文章を進めるか決めてもらう。手順1・3・4は**文章ごとに**行う（plan.json を作るのは Claude の判断で、コマンドでは自動化できない）。

手順5・7もディレクトリを渡せる。`apply <ディレクトリ>` は plan.json がある文章すべてに実行する（ない文章は「skipped」と理由を返す）。採否は文章ごとの plan.json に書くので、文章ごとに採用する案が違ってもまとめて実行できる。確認（手順6）は、すべての文章の主眼と案を1つにまとめて見せて、文章ごとに省略せず承認を得る。

出力された `unitsMd`（単位の一覧）を読む。`learned` にパスがあれば、それも読む（過去の採否から分かった傾向）。

units.md の見方:
- `u12` は削除できる単位。段落は文ごと、リストは項目ごと、コード・表・図・:::ブロックは塊ごと
- `s5` は節（見出しから次の同じレベルの見出しまで、子の節を含む）
- 🔒 は削除できない（frontmatter と `<!-- kuchiku:keep -->` のある節）
- ⚑ は機械ヒント。**判断材料であって、削る理由ではない**

### 3. 主眼の案を決める

主眼は、読者がこの文章から持ち帰るものを一文にしたもの。手順1で書いた主眼と `promise` の候補（出典は構造シートの「主眼」か、文章内の `<!-- promise: … -->`）から一文にする。候補がなければ、タイトルと結論から書く。

ここではまだ本人に聞かない。削除案を作ってから、手順6で案と一緒に1回で確認する。

### 4. 削除案を作る

判定の問いは1つだけ: **「これを消しても、主眼は守れるか」**。

守れると判断したものを、次の5分類のどれかに当てはめる。当てはまらないものは削らない。

| category | 意味 | 例 |
|---|---|---|
| `promise_unrelated` | 主眼と関係ない話 | 比較の文章なのに、片方のツールの歴史を長く説明している |
| `repeat` | 本文の言い直し | まとめの箇条書きが、本文の注意点をそのまま繰り返している |
| `generic` | 主題を別のものに差し替えても成立する一般論 | 「生産性が向上します」というメリットの列挙（Cursor に差し替えても通じる） |
| `preamble` | 予告・前置き | 「本記事では〜について解説します」 |
| `filler` | 情報のない文 | 「いかがでしたか」「今後ますます重要になるでしょう」 |

各案で削除テストに答える。どちらかが true なら、その案は出さない。
- `breaks_repro`: 消すと、読者が手順や検証を再現できなくなるか
- `changes_conclusion`: 消すと、結論や判断の根拠が変わるか

削らないもの:
- 手順、コマンド、数値、条件、判断基準
- 限界、対象範囲、未確認であることの明記、出典
- 構造シートで優先度 A の節
- 結論を先に示す冒頭の「まとめ」（本文の再掲に見えても、読者の判断材料になっているなら残す）

その他のルール:
- 迷ったら提案しない。不要な削除を受け入れさせるより、削り残すほうが害が小さい
- learned.md で「控える」になっているパターンは提案しない。それでも出すなら、理由にその根拠を書く
- 情報密度（低い節に ⚑）は弱い指標。体験談やエッセイの節は、必要でも低く出る
- 同じ理由でまとまる単位は1つの案にする。節を丸ごと消すなら `s番号` で指定する（見出しだけ残る状態を作らない）
- 1つの単位は1つの案にだけ入れる
- 言い換えたほうがよい文は、このスキルの範囲外。案には入れず、最後に「書き換え候補」として3つまで挙げるだけにする

`plan` コマンドは分析だけをする。削る案は Claude が決め、run ディレクトリ（`plan` の出力 `runDir`）に `plan.json`（削除案）として書く。この時点では `promise_confirmed` は `false` で、`accepted` は書かない:

```json
{
  "promise": "本人が確認した主眼の一文",
  "promise_confirmed": false,
  "structure": [
    { "section": "s1", "priority": "C" },
    { "section": "s2", "priority": "A" }
  ],
  "cuts": [
    {
      "id": 1,
      "targets": ["s1"],
      "category": "preamble",
      "reason": "文章の予告だけで、手順に関わる情報がない",
      "breaks_repro": false,
      "changes_conclusion": false
    },
    {
      "id": 2,
      "targets": ["u34", "u35"],
      "category": "filler",
      "reason": "締めの定型句で、主眼に関わる情報がない",
      "breaks_repro": false,
      "changes_conclusion": false
    }
  ]
}
```

`reason` は100字以内で、読者目線の理由を書く。`accepted` と `note` は手順7で書き足す。

### 5. apply: 削除案を検査して見せる（反映しない）

```bash
<skill>/bin/kuchiku apply <文章.md | ディレクトリ>
```

plan.json の `promise_confirmed` が `false` の間、`apply` は plan.json を検査して結果を見せるだけで、文章は変更しない（`"applied": false`）。run ディレクトリに `cut.md`（全案を反映した短縮版）と `report.md` ができ、出力に字数と案の一覧が入る。短縮版が原文から削除しただけでできていることも、ここで機械的に確かめる（`verified`）。

エラーが出たら plan.json を直して、もう一度実行する。

### 6. 本人に確認する（1回で聞く）

次を1つのメッセージにまとめて見せる:
- 主眼の一文
- 構造シート（項目ごとのA・B・C）
- 本文の字数が何字から何字になるか
- 案の一覧（番号・対象・分類・削減字数・理由）

そのうえで、主眼の確認と採否を**一度に**聞く。「主眼はこれでよいか。採用する案の番号は？」。却下するものは、理由を一言もらえると次回の提案に活きる、と添える。

主眼が直されたら、直した文で案を作り直し（手順4）、`apply` をやり直して（`promise_confirmed` は `false` のまま）、もう一度見せる。

### 7. apply: 採用された案を文章に反映する

```bash
<skill>/bin/kuchiku apply <文章.md | ディレクトリ>
```

オプションはない。実行前に plan.json を直す:
- **全ての案**に `"accepted": true`（採用）か `"accepted": false`（却下）を書く。1つでも書き忘れると apply が止まる
- 却下した案に、聞けた理由を `"note": "結論の数値を再提示している"` の形で書く
- 主眼が確認できたので `promise_confirmed` を `true` にする。**これが「反映する」合図**で、`false` のままなら手順5の検査だけで終わる

`promise_confirmed` が `true` の `apply` は、実行のたびに plan.json を検査し直してから、`accepted` が `true` の案を**元の文章に書き込む**（terraform の apply と同じ）。手順5を飛ばしても、plan.json を直したあとでも、最新の内容で反映される。手順6で承認を得てから実行し、実行後に `git diff --stat` を見せる。反映後に同じ文章でもう一度実行すると、文章が変わっているので止まる（二重に反映されない）。

- 採否を `decisions.jsonl` に追記し、`learned.md`（次回の手順2で読む傾向）を更新する
- 採用分だけを反映した `final.md` も run ディレクトリに残す

最後に、何字減ったかを1行で伝えて終える。

## 置き場所

判断ログなどは、対象のリポジトリ直下の `.kuchiku/` に置く（環境変数 `KUCHIKU_HOME` で変えられる）。

```
.kuchiku/
├── decisions.jsonl   … 採否のログ（コミットする）
├── learned.md        … 集計結果（コミットする）
└── runs/<文章のパス>/ … 作業ファイル（.kuchiku/.gitignore が自動で除外する）
```

## 補助コマンド

```bash
# 手で縮めた版が、削除だけでできているかを確かめる
<skill>/bin/kuchiku verify <元の文章.md> <縮めた版.md>

# これまでの採否の傾向を見る
<skill>/bin/kuchiku stats <対象のリポジトリ>
```
